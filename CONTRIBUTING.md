# Start here

This file is for anyone about to change this repository: a person or a coding agent. Read it before touching code. It tells you what the project is, where things live, what you can change freely, what is guarded and why, and how to check and ship a change.

The project has one maintainer and does not take outside pull requests. Security reports go through [SECURITY.md](SECURITY.md).

## What this repository is

`adrian-discord-voice` is the part of A.D.R.I.A.N. that runs in production. It is one Node.js process (`node dist/app/main.js`) that can be, at the same time:

- a **Discord bot**: it sits in one voice call at a time, listens to each member separately, and answers out loud when someone says "Adrian"; it also answers in text chat and has slash commands and typed `!` commands;
- the **server side of the Windows PC app** (the "satellite"), when `satellite.enabled` is on (off by default): a WebSocket on its own port (default 8791), one "room" per connected PC; the PC streams microphone audio, the server does all listening and thinking, and sends back her voice and typed PC actions;
- a small **admin web page** on loopback (default `127.0.0.1:8790`): setup wizard and dashboard.

The PC app itself (Tauri 2, Rust) and its action library live in the main repository, [A.D.R.I.A.N](https://github.com/Riqqqque/A.D.R.I.A.N) (`crates/desktop`, `crates/pc-control`). That repository also holds an older Rust household server, which is not what runs in production.

A spoken turn, in one line: Opus or PCM audio, then Silero VAD per speaker, then local Parakeet speech recognition, then a text wake check for her name, then the conversation controller, then either a local answer (free) or the language model with tools (paid), then speech (local Kokoro, or Piper for Vietnamese; English can go to the Speechify cloud voice when a `cloudVoice` section is configured), then the mixer and back to Discord or the PC. [docs/architecture.md](docs/architecture.md) has the full picture.

## Ground rules

1. **Publishing a release is deploying it.** Servers with `adrian auto-update on` install the latest GitHub release within about an hour, and PC apps update themselves within about six hours. There is no staging step between a tag and every install. Never publish a build that hasn't passed `packaging/package.sh` (which refuses to build unless typecheck and tests pass) and the [clean-install container test](docs/development.md#container-tests). Every release also ships the PC app, so it needs a PC build at the same version (see [Releases](#releases)).
2. **Every paid model call goes through the spend ledger.** `src/limits/usage-ledger.ts` checks the caps before a request and adds the cost after it. Prices come from `brain.priceInPerM` and friends; if they are 0, the dollar caps can never trigger. New model callers must report usage the same way.
3. **Tool results are data, never instructions.** Every tool result and tool error goes to the model through `asUntrustedData`. Text from Discord channels, web pages, song titles, PC clipboards and screens is treated the same way.
4. **Anything with real consequences needs the person's own yes, on their very next turn.** Use `PendingYes`, and give the tool an `asks(result)` predicate plus a `speak` line, so the question goes out word for word and the model never rephrases it. The yes comes from what the person said (`ctx.said`), which the model cannot write. "Okay." is deliberately not a yes. The model can never pass `confirmed` to a PC power action; the server strips it.
5. **Keys go only where they belong.** A config setting may only name a secret meant for its own purpose (`keyName`, `SECRET_PURPOSE` in `src/config.ts`). Keys are never logged, never put in arguments or URLs (Steam's Web API is the one exception, and its errors never carry the URL), and the admin API never returns them.
6. **Integrations stay as read-only as they are.** Plex, Sonarr, Radarr and Steam are lookups. Acting integrations (Home Assistant over MCP, Helix server control) have allow lists and confirmations; don't widen them casually.
7. **Old PC apps must keep working.** The satellite protocol only grows: add optional fields, never require or repurpose one. A PC that doesn't know a new action answers `Unknown PC action`, which the server turns into "needs an update".
8. **Keep heavy work off the main thread.** The mixer writes audio against the wall clock with a 160 ms lead, and Discord heartbeats share the event loop. Smart Turn and calendar expansion run in workers for this reason.
9. **Every config key added after the first release has a default (or is optional).** Adding a required key breaks every existing install on its next update. The few required keys (`guildId`, `channelId`, `secretsFile`, `listen.vadModel`, `listen.asrModelDir`, `brain.model`) are written by the installer and the setup wizard. File paths belong to the installer and can't be set from the browser or `adrian config`.
10. **No personal data anywhere in the repository.** It is public. See [Privacy rules](#privacy-rules-for-code-tests-and-logs).
11. **Don't trust old comments over code.** Some header comments predate features (for example "Nothing here can act" at the top of `src/brain/tools.ts`; "Later milestones ... no implementations yet" above `VoiceActivityDetector` in `src/core/interfaces.ts`, split over two lines; and the `run` comment on `Tool` in the same file, which says tools change only the bot's own state, although PC actions, MCP and Helix tools act outside it). When a comment and the code disagree, the code wins; fix the comment in the same change if you can.

### Never

- Let the model, a tool argument, or text from a channel pick a Discord recipient, a PC, a device or a user.
- Pass `confirmed: true` from model arguments, or add a way for the server to change a PC's policy.
- Add a PC action that types or clicks into other programs, hooks or messages a running game (kernel anti-cheat treats that as cheating), or kills processes.
- Send audio to a cloud service before the local decision that it was meant for her.
- Put a key in a log line, an argument, a URL or an API response.
- Rename the `/api/health` fields, or let auto-update restart her while `busy()` is true.
- Reorder `KOKORO_VOICES`, or move Smart Turn or other heavy work back onto the main thread.
- Commit personal data, local notes files or per-tool agent instruction files. Keep the latter in `.git/info/exclude`.
- Live-test sleep, restart or shutdown on a PC.

## Privacy rules for code, tests and logs

The repository is public, and logs end up in the admin dashboard.

- **No real people.** Don't add real names, nicknames, Discord user, guild or channel IDs, server names, or voice recordings to code, tests, benches, fixtures or docs. Some older tests and benches still use the maintainer's public author name as a sample speaker name (and `bench/turn-bench.py` mentions a set of real recordings, which are not in the repository); use made-up names in new ones. Personal values (owners, the creator's name and how speech recognition misspells it, nicknames) live only in each install's `config.json`. The code under `src/` has no built-in creator; `identity.creator` is optional.
- **Made-up data in tests.** Use invented IDs, documentation addresses (`192.0.2.0/24`, `198.51.100.0/24`, `example.com`), and sample names that are obviously samples. Never use a real LAN address or host name, even a private one.
- **Fake tokens are assembled at runtime.** GitHub push protection blocks token-shaped strings, so tests build fake Discord tokens from parts (see the `DISCORD_TOKEN` fixture in `test/web.test.ts`).
- **No home-directory paths** in code, tests or builds. Release builds must not embed the build machine's paths (`packaging/package.sh` strips the `@discordjs/opus` build folder for this reason).
- **Logs.** Never pass a secret to the logger. As a safety net, `src/core/logger.ts` redacts known key shapes (Groq, Google, Tavily, `sk-` style, Discord bot tokens, argon2 hashes, `sat_` pairing tokens, any long `Bearer` value); add a pattern when you add a key type. Transcripts are logged only when `listen.logTranscripts` (everything, at debug level) or `satellite.logTranscripts` (PC speech judged meant for her, her answers and PC action arguments) is on. Both are off by default. Exceptions, always logged whatever the switches say: music search and request queries (`music search`, `music request` in `src/features/music.ts`) and up to 120 characters of a request that sounded like music but played nothing (`music asked but not played` in `src/app/stack.ts`, with the user ID). Treat production logs as personal data anyway. `AnswerRecord` keeps no user IDs and no words; its `room` is `discord` or `sat:<device id>`.
- **Recordings.** `satellite.recordDays` (0 = off, the default; at most 14) keeps WAV recordings of speech judged meant for her at a PC, with the local and cloud transcripts in an `index.jsonl` beside them, in `<state>/pc-recordings` (folders 0700, files 0600), deleted after that many days (`src/satellite/recorder.ts`, `test/recorder.test.ts`). They are voice recordings of real people: never commit or share them. `adrian backup` includes them (it leaves out only the models).
- **Model inputs.** Other call members' words (room talk), channel history, clipboard and screen contents reach the model as data. Clipboard and screen answers stay out of logs for as long as the history keeps them.

## Cost awareness

Changes move money, not just behavior. Before you change anything on the answer path, read [docs/costs.md](docs/costs.md). In short:

- Local phrases, music orders, slash and typed commands, and alarm commands never call the model. Moving a common request to a local path saves a model call every time; moving one away costs one.
- Every tool schema is sent on every Claude call (cached, but still tokens). A new tool has a standing cost.
- A per-request line placed in the stable part of the prompt breaks the prompt cache on every call.
- Follow-ups that end `SILENT` still cost a model call. Widening follow-up windows or text-chat follow-ups raises spend.
- Speechify characters, Groq transcriptions and Tavily searches are not in the dollar ledger; they have their own budgets or free tiers.
- Real-model benches cost real tokens. Run the ones that match your change, not all of them.

## Before you call a change done

1. `npm run typecheck` and `npm test` pass (see [docs/development.md](docs/development.md) for platform quirks). There is no CI: nothing runs typecheck or tests on push. Run them yourself; `packaging/package.sh` is the only automatic gate, at release time.
2. A test covers the new behavior or the bug, in the matching file from the area table.
3. If you changed prompt wording, tools, routing, follow-up or barge-in timing, music routing or confirmations, you reran the matching real-model bench. Most prompt rules trace to a real complaint; don't remove one without a reason.
4. Docs are updated in the same change:
   - new or changed config key: [docs/configuration.md](docs/configuration.md);
   - new tool or tool argument: [docs/tools.md](docs/tools.md);
   - new user-facing behavior, phrase or command: [docs/usage.md](docs/usage.md);
   - protocol message or field: [docs/satellite.md](docs/satellite.md) and the main repo;
   - new file or module: [docs/codebase-map.md](docs/codebase-map.md);
   - cost-relevant change: [docs/costs.md](docs/costs.md).
5. You fixed or removed any comment your change made untrue.

## Commits

- One author identity for the whole history. No co-author, sign-off or "generated with" lines, and no assistant or vendor names in messages or branch names.
- Subject lines are plain sentences that say what changed for the person using it, for example "Alarms: hear stop through speech slips, and vague snoozes". A release bump commit is titled with the version number alone (for example `0.17.1`).
- Keep unrelated changes in separate commits.

## Releases

Releases are made by the maintainer. The maintainer's release script is not in either public repository, so this list is the full recipe. A release must contain the following, whatever tooling builds it.

**Every release ships the PC app**, even a bump that only changes the bot. The PC app's updater takes the latest release's tag (without its `v`), looks for `adrian-pc-app-<v>-windows-x64.exe` and its `.sha256` on it (a release without them makes every PC report "has no PC app download"), and runs the download with `--self-check` before swapping. It refuses any exe whose output isn't exactly that version (`accepted()` in the main repo's `crates/desktop/src/update.rs`). So every release rebuilds the PC app at the release number.

1. **Versions.** Bump `version` in `package.json`; the bundle name and `/api/health` read it from there (the lockfile's own `version` field is not kept in step today). In the main repo, set `version` in `crates/desktop/Cargo.toml` **and** `crates/desktop/tauri.conf.json` to the same number, written without a byte-order mark (the Tauri build fails on one; Windows PowerShell 5.1's `Set-Content -Encoding utf8` adds it). The build updates the `adrian-desktop` entry in `Cargo.lock`. The bump commit is titled with the version alone here, and `PC app <v>` in the main repo.
2. **Bot bundle.** Build it on Linux x86_64 with `packaging/package.sh release/`. It refuses to build unless `npm run typecheck` and the tests pass, and it writes the bundle and its `.sha256`. `tar -tzf <bundle> | grep build-tmp-napi` should print nothing (that `@discordjs/opus` build folder holds the build machine's paths).
3. **Clean-install test.** Run `test-env/clean-install-test.sh` against that bundle in the systemd container, with the commands in [docs/development.md](docs/development.md#container-tests). It must end with `0 failed`; every check must pass.
4. **PC app exe.** Build `adrian-desktop` in release mode on Windows with the build machine's paths kept out of it, then check it: the build exited 0, the exe's hash differs from the previous release's exe, its file version and the `Cargo.lock` entry equal the release number, `--self-check` prints exactly that number, and your user name is not in the file. Commands are in [docs/development.md](docs/development.md#building-the-pc-app-for-a-release).
5. **PC app zip.** `adrian-pc-app-<v>-windows-x64.zip` holds exactly three files at its top level: `ADRIAN.exe` (the exe from step 4, renamed), `Install.ps1` (from the main repo's `crates/desktop/packaging/`; it installs the `ADRIAN.exe` beside it), and `README.txt` (short install steps: turn on `satellite.enabled`, `adrian satellite add`, run `Install.ps1 -Server ... -Token ...`, the SmartScreen warning, links to [docs/pc-app.md](docs/pc-app.md) and the source). The exe inside must be byte for byte the bare exe asset.
6. **Checksums.** One `.sha256` per asset, in `sha256sum` format (`<hash>  <name>`, a bare file name, LF line end, no byte-order mark). From the folder holding the file, in bash: `sha256sum --text <file> > <file>.sha256`. `--text` matters in Git Bash on Windows, whose `sha256sum` otherwise writes `<hash> *<name>`. Don't use a Windows PowerShell 5.1 `>` redirect: it writes UTF-16.
7. **Publish** a GitHub release tagged `v<version>` on this repository with six assets:
   - `adrian-voice-<v>-linux-x64.tar.gz` and `.sha256` (used by `install.sh`, `adrian update` and the Docker build);
   - `adrian-pc-app-<v>-windows-x64.exe` and `.sha256` (the PC app's self-updater looks for this exact name, and only under this repository's `releases/download/` URLs);
   - `adrian-pc-app-<v>-windows-x64.zip` and `.sha256` (manual PC install).

   Then download the public assets once and check them against their checksums. Publishing is deploying: servers with auto-update install it within about an hour and PCs within about six hours.

Releases are protected by checksums from the same release, not signatures. Whoever can publish a release can run code on every auto-updating server and PC; see [docs/security.md](docs/security.md).
